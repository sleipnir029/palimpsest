## 2026-05-27 — T10
**What:** The first GitHub Actions build pushed fine to Docker Hub but RunPod refused to start the pod: `failed to pull image: layers from manifest don't match image configuration`. Cause: `docker/build-push-action@v6` (buildx ≥0.10) attaches a provenance attestation by default, publishing a multi-manifest OCI index (image manifest + in-toto attestation manifest). RunPod's image puller walks the index, hits the attestation entry whose config is not an image, and the diff_ids mismatch. Docker Hub renders the index fine, so the image *looked* healthy. Fixed by adding `provenance: false` + `sbom: false` to the build step so buildx pushes a plain single-image manifest; re-ran the workflow on the same tag.
**Verdict:** accepted (external-tooling default, not a Dockerfile bug)
**Lesson:** A "successfully pushed" image on Docker Hub is not proof it will run — buildx attestations make an OCI index that some container runtimes (RunPod) reject; for BYO-container targets, build with `provenance: false`.

## 2026-05-27 — T10
**What:** The card specifies `CMD ["bash"]` ("interactive — gpu_provider will SSH in"). On RunPod the container starts detached, so `bash` as PID 1 hits EOF and exits immediately. We first saw `Container ... is not running` and attributed it to this; the next attempt's system log revealed the early failures were at least partly the CUDA-12.9 nvidia init hook (see next entry), which blocks container creation *before* PID 1 regardless of CMD. Both fixes were still needed: on the working 12.8 host the container stays up only because `CMD` is now `["sleep", "infinity"]` (a bare `bash` would have exited there too). Immediate unblock used the RunPod template's *Container Start Command* override (`sleep infinity`); the Dockerfile change bakes it in.
**Verdict:** accepted (card's CMD is platform-incompatible)
**Lesson:** A RunPod custom container needs a long-lived foreground PID 1 (`sleep infinity`); `CMD ["bash"]` only works when a TTY is attached, which a detached pod start does not provide.

## 2026-05-27 — T10
**What:** Corrected the CUDA base from **12.9.1 → 12.8.1** (and torch/vLLM cu129 → cu128). The 12.9 image failed at the nvidia container-init hook on RunPod: `unsatisfied condition: cuda>=12.9, please update your driver`. Measured RunPod's available host drivers via the deploy page's CUDA-version filter: **ceiling is 12.8** (2× RTX 3090 available). 12.8 is also vLLM 0.19.1's lowest supported CUDA and the version olmOCR's official Docker image ships, with Chandra needing only 12.1+ and MinerU on torch cu128 — so all four parsers (T11-T13) share the 12.8 base. The earlier 12.9 choice (preceding entry) maximized version-cleanliness but ignored the binding constraint: the host driver caps the runnable CUDA, and I had not measured it.
**Verdict:** accepted (corrects the 12.9 over-reach with host data)
**Lesson:** The GPU **host driver** — not vLLM's default, not the parsers — is the binding constraint on CUDA version; measure the target hosts' supported CUDA *before* pinning a base image. The build-time `+cuXXX` assert proves image-internal consistency, never host compatibility.

## 2026-05-28 — T12
**What:** `runpod-template.md` first documented the olmOCR pod's Container Start Command as `-c "sleep infinity"`, reasoning that the upstream image's `ENTRYPOINT ["/bin/bash"]` would receive it as arguments (the way `docker run … olmocr -c "olmocr …"` does). On the first pod the container exited immediately — proxy SSH authenticated but reported `container … is not running`. RunPod **shell-wraps** the Container Start Command (`sh -c "<field>"`) instead of appending it to the image ENTRYPOINT, so `sh -c '-c "sleep infinity"'` tried to execute a command literally named `-c`. Corrected to bare `sleep infinity`; template + PROGRESS updated. (Model verification — `--help`, baked weights path, FP8 init — still deferred: no GPU available when tried.)
**Verdict:** accepted (corrected my own wrong instruction, empirically rather than from docs)
**Lesson:** RunPod's "Container Start Command" is run **through a shell**, not appended to the image's ENTRYPOINT — give it a bare command (`sleep infinity`), never Docker ENTRYPOINT-style args (`-c "…"`). Same container-liveness need as T10's `CMD ["sleep","infinity"]`, opposite-looking mistake: T10 was the image's baked CMD, this is the platform's field semantics.

## 2026-05-28 — T13
**What:** The first CI build of the Chandra image (commit d0d634b) failed at the build-time assert: `ModuleNotFoundError: No module named 'vllm'`. The card's premise "Chandra brings its own torch/vLLM (not pinned)" is wrong — base `pip install chandra-ocr` 0.2.0 installs only the OpenAI-API **client** (openai, httpx, pypdfium2, markdownify, pydantic…); it bakes **no model runtime** (no vllm, no torch, not even numpy — the build log's `Successfully installed` list confirms it). Chandra's "vLLM backend" means it talks to a *separately run* vLLM OpenAI server, and its `chandra_vllm` helper launches a **Docker container**, which doesn't fit a single RunPod pod container. The `import vllm` I had added to the cu128 assert (prior session, on advisor's suggestion, as a runtime-contract check) is exactly what surfaced this — for free, in CI, instead of on a paid pod. Per user decision, switched the image to the **HuggingFace backend**: `pip install "chandra-ocr[hf]"` (torch + transformers, in-process), run `chandra … --method hf`; the assert is now `import torch, torchvision, transformers` (all import GPU-free, so they are safe in the no-GPU CI builder; torch and torchvision are both `+cu128`-checked — torchvision is the `[hf]` dep most likely to resolve off the cu128 index and split the CUDA ABI, caught in independent review).
**Verdict:** accepted (card's runtime assumption was wrong; corrected the design, caught at zero cost in CI rather than on a paid pod)
**Lesson:** "pip install <tool>" does not imply the tool can run a model — some OCR packages ship a thin API client and expect you to bring the server/runtime. Read the `Successfully installed` list, not the backend's name. A build-time `import <runtime>` assert earns its keep: it converted a would-be paid-pod failure into a free red CI build.

## 2026-05-29 — T14 (live verification)
**What:** Ran the deferred live test on a real pod (per user). Several findings. (1) **Template ≠ pod:** the user first handed a *pod* ID (`4jgvnguwlf55a1`) as a "template"; `RunPodSession` creates its own pod *from a template*, so the create 500'd (`template not found`). Worse, a docling *pod* the user had started was left RUNNING at $0.86/hr (~$0.27 over 19 min) — surfaced it (didn't stop it myself, I hadn't created it); user terminated it. (2) **Parser images have no sshd:** the four palimpsest images can't be reached by `RunPodSession`'s direct TCP SSH (their template notes say so) — so T14's SSH design is incompatible with the parser images. **This is a T16 decision** (add sshd to the images, or proxy-exec + a network-volume file transfer); `scp_up`/`scp_down` are likewise untested against them. For T14 (whose live test is just `echo hello` → image-agnostic) I created a base sshd template (`runpod/pytorch:0.7.0-cu1241-torch241-ubuntu2204`, `PUBLIC_KEY` injected). (3) **Availability is dynamic — "Low" stock ≠ deployable:** every cheap GPU (4070Ti/4090 community, A5000/L4 secure, all "Low") returned `This machine does not have the resources to deploy your pod` (capacity 500, no pod, no charge); only H100/H200 ("High") actually deployed. Per user, made `gpu_type` accept `str | list[str]` → `gpuTypeIds` array → RunPod allocates whatever's in stock; the live test reads a cheapest-first `RUNPOD_GPU` list + `RUNPOD_CLOUD` from env (production default stays the single 4090/community). Ran on H100 with an env-raised cost cap (`RUNPOD_MAX_EUR`, default still the card's €0.10). (4) **Real bug only a live run could catch:** fabric's `Connection.run()` forwards stdin by default → `OSError: reading from stdin while output is captured` under pytest/CI/any non-interactive caller (and T16's parser runs are non-interactive) → fixed with `in_stream=False`. The first H100 run hit this and still tore the pod down cleanly (verified EXITED), proving the `__exit__`-on-exception teardown on real HW. (5) **Pass:** second run green — pod created → direct TCP SSH (account key injected) → `echo hello` → positive GPU ledger entry (< cap) → torn down. Terminated all test pods afterward (0 remaining). Spend ≈ $0.26 (two H100 runs; failed cheap-GPU creates were $0). Base template `klmsdkf0jd` kept for future live/T16 runs.
**Verdict:** accepted — live-verified; the stdin-forwarding bug and the dynamic-availability handling were only discoverable by running on real hardware, and the teardown held even on the failing run.
**Lesson:** RunPod "Low" stock is not a deployability promise — only an actual create tells you, so pass a GPU *list* and fall back across GPUs/clouds; and a green dry-run that mocks SSH can't catch transport bugs (stdin forwarding) — the live test paid for itself. (Open T16 input: parser images need an sshd story before `RunPodSession` can drive them, and `scp_up/scp_down` remain unproven.)
